## 알려진 품질 문제와 처리

1. 날짜 형태의 노선번호 9개: `07월 01일`, `07월 02일`, `07월 03일`, `08월 01일`, `10월 01일`, `11월 01일`, `12월 01일`, `01월 13일`, `01월 16일`. 번호를 추측하지 않고 “번호 미확인(ID …)”으로 표시한다.
2. 노선 ID `250052403`에는 `남산5(남산504)`와 `동면1(동면101)`이 혼재한다. 다수결로 번호를 정하지 않는다. 이 항목까지 총 10개 노선의 번호가 미확인이다.
3. 정류장 `250026916`은 과거 `장학2리입구`, 최신 `장학17리입구`이며 좌표 차이가 약 1.4m다. 최신 명칭·좌표가 유일하고 차이가 10m 이내라 조회 시 최신값을 사용한다. 원본은 수정하지 않는다. 같은 날짜에 충돌하거나 10m를 넘는 자료는 후보에서 제외하고 연결 구간을 끊는다.
4. 한 노선이 같은 정류장 ID를 여러 번 방문할 수 있다. `(노선 ID, 정류장순서)`를 유지하며 ID 중복 제거로 방문을 없애지 않는다.
5. 상·하행, 회차별 연속 운행, 시간표·실제 주행 궤적이 없다. 경로는 순서 기반 후보이며 실제 탑승 가능 여부·전체 도착시간을 확정할 수 없다.

숫자 노선·정류장 ID는 춘천 TAGO의 `CCB` 접두사를 붙여 다룬다. 노선번호나 정류장명으로 실시간 자료를 억지 매칭하지 않는다. CSV와 실시간 도착값이 같은 정류장·노선 ID일 때만 참고값을 표시한다. ID 일치도 방향 검증을 대신하지 않는다.

## 데이터 담당자가 교체할 때

담당: 권오준. 호출 코드·필드 계약 변경은 이준엽과 먼저 협의한다.

1. 원 제공처의 새 자료에서 열 이름·인코딩·기준일·ID·순번을 확인한다. 엑셀에서 열었다 저장하며 노선번호를 날짜로 변형하지 않도록 주의한다.
2. 파일명 변경 시 `app.py`의 경로와 실제 CSV 통합 테스트를 함께 변경한다. 동일 파일을 갱신해도 원본 출처와 새 해시를 이 문서에 기록한다.
3. `python3 -m unittest discover -s tests`로 회귀 검증한다. Windows는 `py -m unittest discover -s tests`를 사용한다. 의도적으로 자료를 갱신한 경우 실제 자료 건수·기준일 검증도 새 원본과 대조한 뒤 갱신한다.
4. 서버를 재시작한다. CSV는 프로세스에서 최초 조회 시 한 번 읽고 메모리에 보관한다.
5. 원본 변경과 검증 결과를 데이터 작업 커밋·PR에 기록한다. CSV만으로 확인되지 않은 운행 정보를 채워 넣지 않는다.

실행·응답 계약·한계는 `docs/TRANSIT_ROUTING.md`를 참고한다.
