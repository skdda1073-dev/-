# 한림대학교 셔틀 시간표와 경로 후보

## 범위

셔틀 원본을 읽고 검증하는 기능과 시간표·경로 후보를 계산하는 기능을 분리한다. 기존 시내버스 조회와 응답 계약은 유지하며, 셔틀은 `출발지 → 도보 → 셔틀 승차 → 셔틀 하차 → 도보 → 목적지`인 단일 차량 구간만 대상으로 한다. 시내버스와 셔틀 사이의 환승은 포함하지 않는다.

운영 설정은 원본 CSV에 공식 운행 조건과 사용자가 승인한 대표좌표를 연결하는 프로필을 적용한다. 연결 가능한 출발·도착에는 접근 도보·탑승 여유를 반영한 셔틀 후보를 기존 시내버스 후보와 함께 반환한다. 대표좌표는 정확한 셔틀 승강장이 아니며 실시간 출발·도착도 확인하지 않으므로 실제 탑승을 확정하지 않는다. 좌표 연결이 없는 정류장의 시간표도 별도로 조회할 수 있다.

공식 자료에 있는 제5노선은 직원 노선이므로 이번 학생 통학 조회 범위에서 제외한다. HTML·CSS·프론트엔드 동작은 변경하지 않는다.

이 문서는 **백엔드 PR의 API 계약과 고경완 UI 담당자의 인수 문서**다. 게시 기준 `main`의 `ui-renderer.js`는 정류장 배열의 `find`·`forEach`를 사용하는 화면이며 `mode: "journeys"` 객체를 처리하지 않는다. 이는 이 셔틀 변경 전부터 존재한 `main`의 목적지 경로 API와 화면 사이의 불일치다. 백엔드 PR의 14개 파일에 UI 수정은 포함하지 않으며, 최신 디자인을 유지한 응답 분기·표시 어댑터를 별도 UI PR로 연결해야 한다. 현재 상태를 사이트 전체 연동 완료로 해석하면 안 된다.

모든 파일 경로와 아래 명령은 **저장소 루트** 기준이다. 먼저 `git rev-parse --show-toplevel`로 작업 위치를 확인하고, 저장소 안의 `-/` 등 예전 복제 폴더를 수정하지 않는다.

## 실제 원본과 파생 구조

사용하는 원본은 프로젝트 루트의 `한림대_셔틀버스.csv`다. 파일은 UTF-8이며 헤더를 제외한 데이터 196행, 원문 정류장명 31개를 담고 있다. 헤더를 포함한 파일 행 수는 197행이다. 열은 아래 네 개이며 좌표·정류장 ID·운행일 열은 없다.

| 열 | 원문 예 | 해석과 제한 |
| --- | --- | --- |
| `노선명` | `제2노선` | 노선 구분. 시내버스의 노선 ID와 합치지 않음 |
| `방면` | `온의동/퇴계동/석사동` | 원문 방향·지역 설명을 보존 |
| `정류장` | `온의금호1차 버스정류장` | 셔틀 정차 위치를 나타내는 원문 명칭 |
| `시간` | `07:58` | 정류장에 기재된 시각. 도착인지 출발인지 원문에 설명 없음 |

31개는 서로 다른 **원문 명칭**의 개수이며, 검증된 물리 정류장 31곳이라는 뜻이 아니다. `한국교직원공제회`와 `교원공제 회관`, `케이티앤지 버스정류장`과 `KT&G 버스정류장`처럼 비슷한 명칭을 같은 위치로 자동 병합하지 않는다. 대표점 대응은 아래 프로필의 수동 화이트리스트만 적용한다.

원본을 새 파일 형식으로 변환하거나 내용을 덮어쓰지 않는다. 저장소 모듈이 원문 행·행 번호를 보존한 채 런타임 메모리에 노선, 방향, 회차, 회차 안의 정류장 순서, 시각을 파생한다. `data/hallym_shuttle_profile.json`은 원본을 대체하는 시간표가 아니라 공식 근거·운행 규칙·대표점 대응을 담은 별도 보완 자료다. `services/shuttle_profile.py`가 프로필을 검증해 메모리상의 원본 스냅샷에 적용한다. 생성한 내부 ID는 원문 데이터의 공식 ID가 아니다.

검증 시 원본 SHA-256은 `7755f5982aa671785e59ea5b528b12048bcb9210b715ba3e4dc13d0f18d9f03d`다. 인코딩·해시·행 수를 응답의 `source`에 제공한다. `route_id`는 노선명·방면, `trip_id`(원시 회차의 `id`)는 노선명·방면·시작 행, `stop_id`는 노선명·방면·정류장명을 각각 구분해 만든 안정적인 내부 ID다. 같은 회차의 출발·종착에 같은 `stop_id`가 나타나도 원문 방문 행을 모두 보존한다. 저장소는 최초 조회 후 메모리에 캐시하므로 원본을 교체한 뒤에는 서비스를 재시작해야 한다.

원본 CSV는 **UTF-8·LF 줄바꿈과 바이트 내용을 그대로 보존**해야 한다. 스프레드시트에서 다시 저장하거나 에디터·체크아웃 과정에서 CRLF로 바꾸는 것만으로도 해시가 달라져 공식 프로필이 적용되지 않는다. macOS/Linux에서는 `shasum -a 256 "한림대_셔틀버스.csv"`로 위 해시와 비교할 수 있다. 해시 불일치를 없애려고 프로필의 해시만 임의로 고치지 말고 인코딩·줄바꿈·데이터 변경 원인을 먼저 확인한다.

| 노선 | 원본 구조 | 메모리에서 다루는 단위 | 원본에서 확인되는 한계 |
| --- | --- | --- | --- |
| 제1노선 | 등교 13행, 하교 3행 | 정류장 한 곳만 있는 16개 시각 항목 | 등교는 `춘천역`, 하교는 `대학교`만 기재되어 상대 종점과 구간 시간이 없음 |
| 제2노선 | 72행 | 12행씩 6회차 | 대학교에서 시작해 대학교로 돌아오는 원문 순서 |
| 제3노선 | 16행 | 8행씩 2회차 | 대학교에서 시작해 대학교로 돌아오는 원문 순서 |
| 제4노선 | 92행 | 15·15·15·16·16·15행의 6회차 | 일부 저녁 회차에만 `춘천역` 행이 있음 |

제2~4노선은 원문에서 반복되는 `대학교` 시작·종료 행과 그 사이 정류장 시각의 연속 순서로 회차를 구분한다. 공식 회차 ID나 별도 정류장순서 열이 있어 이를 그대로 읽는 구조는 아니다. 같은 노선 이름이라고 이전 회차의 끝과 다음 회차의 시작을 이어 타는 후보를 만들지 않는다.

특히 **헤더를 포함한 원본 135행과 136행**은 모두 `제4노선,신사우동/후평동,대학교,09:40`이다. 135행은 앞 회차의 마지막 행이고 136행은 다음 회차의 첫 행인 원문 경계로 각각 보존한다. 단순 중복 제거로 둘 중 하나를 삭제하거나 두 회차를 연결하지 않는다. 저녁에만 원문에 등장하는 `춘천역`을 다른 회차의 중간 정류장으로 보충하지 않는다.

원본만 읽으면 제1노선은 승하차 구간을 만들 수 없다. 운영 프로필은 공식 자료로 확인한 `춘천역 → 대학교` 등교와 `대학교 → 춘천역` 하교를 별도 근거가 있는 구간으로 보완한다. 원본에 없는 상대편 정류장의 파생 이벤트는 `time: null`로 두고 공식 근거에서 보완한 항목임을 표시한다. 도착시각은 생성하지 않는다. 공식 확인된 원래 출발 정류장의 시각만 `scheduled_departure_at`에 넣는다.

제2~4노선은 같은 원본 회차에 실제로 존재하는 순방향 구간만 사용하며, 프로필로 누락된 중간 정류장이나 다른 회차를 이어 붙이지 않는다.

## 공식 프로필과 운행 조건

원본에는 다음 정보가 없다.

- 운행요일, 학기·방학 구분, 공휴일·운휴일, 시간표 적용 시작·종료일
- 탑승 대상, 요금·무료 여부, 예약·학생증 등 탑승 조건
- 공식 정류장 ID와 승차 위치 좌표, 도로 반대편 구분
- `시간`의 도착·출발 의미, 차량 실시간 위치·도착 정보

운영 프로필은 공식 운행 안내와 2026년 학사·공휴일 자료에서 확인한 범위만 추가한다. 원본에 없는 정보를 원본 열의 값처럼 표시하지 않고 공식 출처와 적용 기간을 함께 남긴다.

공식 근거 확인일은 모두 **2026-10-18**이다. 상세 인용 범위와 원문 출처는 프로필에도 보존한다.

실제 CSV에는 운휴 조건이나 자정을 넘는 시각이 없다. 2026년 학기·휴일·금요일 예외는 공식 근거를 담은 프로필로 적용하며, 자정을 넘는 시각은 합성 fixture로만 검증한다. 합성 조건을 실제 학교 운행 조건으로 취급하지 않는다.

프로필에는 적용 대상 원본의 SHA-256을 고정한다. 원본 해시가 일치하지 않으면 해당 프로필의 보완·규칙·대표점 대응을 적용할 수 없다. 새 CSV를 넣었다면 공식 자료와 대응을 다시 검토하고 프로필을 갱신해야 한다. 프로필이나 시내버스 좌표 자료에 문제가 있어도 원본 시간표 조회를 독립적으로 유지하고 원인을 진단 정보로 제공한다.

| 파일 | 책임·호출 관계 |
| --- | --- |
| `services/shuttle_repository.py` | 원본 읽기·인코딩·열·행 검증, 원문 보존, 노선·방향·회차·정류장 시각의 메모리 파생. 셔틀 서비스가 호출 |
| `data/hallym_shuttle_profile.json` | 공식 출처·확인 범위, 원본 해시, 2026년 운행 규칙, 수동으로 정한 대표점 대응. 원본 CSV를 보존하는 보완 자료 |

| `services/shuttle_service.py` | 시간표 조회, 날짜·운행 조건 상태, 승하차 순서, 접근 도보와 탑승 여유를 고려한 시간표 후보 계산. 저장소와 기존 도보 함수 사용 |
| `services/transit_service.py` | 시내버스 결과와 셔틀 조회 상태·후보를 통합. 공급자 한쪽의 오류가 다른 쪽 조회를 막지 않도록 분리 |
| `services/route_planner.py` | 기존 시내버스 경로 계산 유지. 필요한 후보 정렬·개수 제한 연결만 최소 변경 |

| `tests/test_shuttle*.py` | 실제 원본 읽기와 합성 자료의 시간·조건·오류 경계, 기존 API 통합을 외부 호출 없이 검증 |

비어 있거나 잘못된 행은 원문 행 번호와 사유를 진단 정보로 남기고 정상 회차까지 통째로 잃지 않도록 처리한다. 순서·시각 검증 실패가 있는 구간을 건너뛰어 가짜 직통 구간을 만들지 않는다. 오류 메시지에 비밀값이나 개인 절대 경로를 포함하지 않는다.

### 대표좌표 대응

원래 서비스의 `stop_id → {lat, lon, evidence}` 주입 구조에 대표점의 근거·근사 여부를 추가한다. 프로필을 주입하지 않은 서비스는 자동으로 이름을 연결하지 않는다. 운영 앱은 승인된 프로필의 수동 바인딩을 주입한다.

`대학교`에는 `한림대학교 건물별 좌표.csv`의 `Campus Life Center` 좌표 **37.88632, 127.73812**를 사용한다. 공식 `CLC 희망터 앞` 승차 안내는 제1노선에 해당한다. 제2~4노선의 `대학교`에도 같은 좌표를 쓰는 것은 사용자가 승인한 캠퍼스 대표점 적용이며, 해당 노선의 정확한 승강장이 CLC라고 공식 확인했다는 뜻이 아니다.

원문 명칭 31개 중 22개 명칭에 대표점을 연결한다. 이는 `대학교` 1개와 교외 명칭 21개이며, 검증된 셔틀 승강장 22곳이라는 뜻이 아니다. 교외는 기존 시내버스 정류장 등의 대표점을 수동 화이트리스트로 대응한다. 가까운 좌표나 유사한 이름을 런타임에 자동 확정하지 않는다. 매핑된 시내버스 정류장 좌표도 정확한 셔틀 승강장 좌표로 승격하지 않는다. 공제회·CGV·칠전동 영화루·퇴계주공 505동·세경4차·이마트24·석사진흥A·써브웨이 등 근거가 부족한 나머지 명칭은 GPS 승하차 연결에서 제외하되 시간표는 남긴다.

승하차 정류장과 `access_walk`·`egress_walk`에 다음 정보를 보존한다.

| 필드 | 의미 |
| --- | --- |
| `location_basis` | 건물·시내버스 정류장 등의 대표점 사용 근거 |
| `reference_name` | 실제 도보 계산에 사용한 대표 장소명 |
| `official_stop_name` | 공식 안내명 또는 CSV 원문 명칭. 교외에는 원문 정류장명도 들어가므로 필드명만으로 공식 승강장 검증을 뜻하지 않음 |
| `is_approximate` | 정확한 셔틀 승강장이 아닌 대표좌표인지 여부 |
| `stop_location_verified` | 정확한 셔틀 승강장 위치 검증 여부. 대표점 연결은 `false` |

후보에는 `location_is_approximate`를 제공하고 지도 좌표의 기준을 `path_basis: "reference_points"`로 구분한다. 중간 좌표가 없으면 기존처럼 `path: []`를 반환한다. 대표점들이 모두 있어도 연결선을 실제 도로·셔틀 궤적으로 표시하지 않는다.

## 시간과 대기 계산

시간은 모두 `Asia/Seoul`로 처리한다. 조회 시각은 서비스 호출에서 주입할 수 있어 테스트에서 고정할 수 있으며, 운영체제의 기본 시간대를 사용하지 않는다. API에서 명시한 시각에는 UTC offset이 필요하다. 예를 들어 `2026-10-18T07:50:00+09:00`이나 동등한 UTC 시각을 받아 한국 시간으로 해석한다.

기준시각을 명시하지 않은 현재 경로 조회는 보행 응답을 받은 뒤 시계를 다시 확인하여 조회 지연 때문에 놓친 편을 제외한다. 후보의 `query_at`은 이 재확인한 계산 기준시각이며, 최상위 `query_at`은 조회 시작 기준이다. 명시적 `query_at`을 넘긴 테스트·과거 조회는 그대로 고정한다. 서비스 내부의 naive datetime은 명시적으로 한국 시각으로 해석하지만 HTTP `at`은 offset 없는 입력을 거절한다.

기본 탑승 여유는 1분이다. 기존 `services/route_planner.py`의 `BOARDING_MARGIN_MIN = 1.0`과 일치하도록 둔 **앱의 설정값**이며 학교의 공식 탑승 규정이나 검증된 승차 소요시간이 아니다. 응답에 실제 적용값을 제공한다.

조회 시각을 `at`, 확인된 접근 도보시간을 `access`, 여유시간을 `margin`이라고 하면 아래 기준을 사용한다.

```text
ready_at = at + access + margin
시간표 후보 조건 = scheduled_stop_at >= ready_at
wait_min = scheduled_stop_at - ready_at
```

접근 도보 중 지나가는 편은 제외한다. 여유시간까지 포함해 승차 준비가 끝나는 시각과 시간표 시각이 같으면 경계상 후보가 될 수 있지만, 실제 운행 및 `시간`의 의미가 미확인이라는 상태는 유지한다. 대기는 음수가 될 수 없고 접근 도보를 대기에 다시 더하지 않는다. 여유시간도 별도 필드로 제공하여 확인 가능한 시간 합계에서 누락하거나 중복하지 않도록 한다.

대표좌표를 사용한 `ready_at`은 해당 대표점까지 도보와 앱 여유를 반영한 조건부 준비시각이다. 대표점에서 실제 승강장까지 필요한 미확인 시간을 만들어 더하지 않는다. 출발지가 CLC 건물 좌표와 같아 접근 도보가 0분으로 계산되어도 정확한 승강장까지 0분을 확인한 것은 아니다. `is_approximate`·`stop_location_verified`와 경고를 함께 전달한다.

이미 지난 시각은 다음 편으로 표시하지 않는다. 해당 조회일의 남은 항목이 없으면 그날의 시간표 항목이 소진됐다는 상태를 구분하고, 실제 다음 운행일은 만들어 내지 않는다. 저장소는 `00:00~47:59`를 서비스 날짜 자정 기준 분으로 보존한다. 명시적인 `24:xx` 이상만 실제 다음 날짜로 계산하고, 회차 안에서 `23:50→00:10`처럼 시각이 감소하면 자동 이월하지 않고 오류로 기록한다. 자정 직후에는 명시적 24시 이상 시간표에 한해서 이전 서비스 날짜도 검토한다. 실제 원본에 이월 시각은 없으며 합성 자료로만 검증했다.

원본 시각의 차이인 `scheduled_segment_min`을 제공할 수 있으나 이를 실측 차량 이동시간이나 확정 소요시간으로 승격하지 않는다. `시간`의 도착·출발 의미와 운행 조건이 확인되지 않았으므로 출발시각·도착시각·총 소요시간은 확인 가능한 경우에만 채운다. 정보 부족을 `0`분으로 대체하지 않는다.

제1노선은 공식 확인된 원래 출발 이벤트에만 출발 의미를 적용한다. 보완한 상대 종점의 시각이 없으므로 `scheduled_arrival_at`·`scheduled_alight_stop_at`·`scheduled_segment_min`·`ride_min`·`total_min`은 `null`이다. 제2~4노선의 `시간`은 계속 의미 미확인이므로 `scheduled_departure_at`·`scheduled_arrival_at`을 채우지 않는다. 운영 프로필의 대표점 기반 후보는 모두 `availability_confirmed: false`이며 전체시간을 확정하지 않는다.

## API와 필드 의미

### 시간표 조회

`GET /shuttle_timetable`은 실시간 버스 도착 키 없이 로컬 원본과 프로필을 조회하는 진입점이다. 좌표 자료가 없거나 시내버스 좌표 로딩에 실패해도 시간표 조회는 별도로 유지한다. 외부 API를 호출하지 않는다.

| 매개변수 | 의미 |
| --- | --- |
| `route` | 노선 필터 |
| `direction` | 원문 방면 필터 |
| `board` | 승차 정류장 필터 |
| `alight` | 하차 정류장 필터. 승차 정류장과 같은 회차의 뒤 순서인지 검증 |
| `at` | 조회 기준 시각. 지정할 때 ISO 8601 형식과 offset 필수 |

`route`·`direction`은 원문 문자열의 정확한 일치로 필터한다. `board`·`alight`는 정확한 내부 정류장 ID를 우선 찾고, 없으면 원문 명칭의 정확한 일치로 찾는다. 같은 명칭이 여러 노선·방향의 서로 다른 ID에 해당하면 `ambiguous_stop`으로 반환하므로 노선·방면 또는 ID를 함께 지정해야 한다. 유사어·띄어쓰기 교정으로 자동 연결하지 않는다.

응답은 `mode: "shuttle_timetable"`, `trips`, `routes`, `stops`, `timetable_candidates`, `source`, `conditions`, `diagnostics`, `warnings`, `query_at`, `timezone`를 포함한다. `trips`는 원시 시각을 보존한 회차 목록이다. 승하차 필터를 모두 지정해야 같은 회차의 앞→뒤 `timetable_candidates`를 만든다. 이 후보는 조회시각 이후의 시간표 항목만 고르며 도보·탑승 여유를 가정하지 않는다(`selection_basis: "timetable_only_without_access_walk"`). 접근 도보가 포함되는 계산은 경로 서비스에서 수행한다.

| `status` | 의미 |
| --- | --- |
| `unknown_calendar` | 날짜별 실제 운행이 미확인인 시간표 참고값 |
| `ok` | 공식 프로필 또는 주입한 검증 달력의 적용 범위에서 조건을 반영한 결과. 정확한 승강장·실제 탑승까지 확정한 뜻은 아님 |
| `unmatched` | 시간표 필터가 미매칭이거나 GPS 경로에 필요한 좌표 연결 부족 |
| `ambiguous_stop` | 같은 이름의 정류장 ID가 여러 개여서 확정 불가 |
| `no_connection` | 지정 노선·순서·회차에서 구간을 구성할 수 없음 |
| `no_departures_remaining` | 조회 서비스 날짜에서 준비시각 이후의 시간표 항목이 없음 |
| `not_operating` | 확인된 학기 밖·요일·공휴일·운휴 조건에 해당 |
| `walking_unavailable` | 경로에 필요한 도보 계산 실패 |

2027년처럼 운행일 근거 범위 밖은 미확인으로 남기므로 `no_departures_remaining`이 실제 그날 운행을 확인했다는 뜻은 아니다. `at` 형식·범위 오류는 HTTP 400/`INVALID_SHUTTLE_QUERY`, 시간표 파일 읽기·헤더 오류는 HTTP 502/`SHUTTLE_DATA`다. 시간표 목록은 확인되지 않은 탑승 조건까지 충족하는 이용 가능 편 목록을 의미하지 않는다.

프로필 파일의 형식·원본 해시 검증에 실패해도 원본 자체의 정상 시간표는 별도로 조회한다. 이 경우 `profile_status: {"status":"error","code":"SHUTTLE_DATA"}`와 경고를 붙이고, 공식 종점 보완·운행 달력·대표좌표 연결을 적용하지 않는다. 원본 자체를 읽지 못하면 HTTP 502를 유지한다. 경로 조회의 프로필 실패는 `providers.shuttle` 오류로 격리하며 정상 시내버스 후보는 반환한다. 승하차를 모두 지정하지 않은 원시 회차 목록에는 `operation_status_at_query_date`를 붙여 금요일 제외편 등을 구분한다.

### 시간표 요청·응답 예시

아래는 공식 프로필을 적용한 월요일 시간표 계약 예시다. URL은 `URLSearchParams`로 만들면 한국어·공백과 offset의 `+`가 안전하게 인코딩된다. 주소에 직접 쓰는 경우 `+09:00`의 `+`를 `%2B`로 인코딩해야 한다.

```javascript
const query = new URLSearchParams({
  route: "제1노선",
  direction: "춘천역 방면 (등교)",
  board: "춘천역",
  alight: "대학교",
  at: "2026-10-19T07:50:00+09:00"
});
fetch(`/shuttle_timetable?${query}`);
```

첫 후보의 핵심 필드만 발췌하면 아래와 같다. `timetable_candidates`는 도보를 계산하지 않으므로 대기는 `null`이다. 날짜별 운행 조건이 확인되어도 실제 탑승은 확정하지 않는다.

```json
{
  "mode": "shuttle_timetable",
  "status": "ok",
  "query_at": "2026-10-19T07:50:00+09:00",
  "timezone": "Asia/Seoul",
  "time_basis": "schedule",
  "realtime": false,
  "timetable_candidates": [{
    "transport_type": "shuttle",
    "route_name": "제1노선",
    "direction": "춘천역 방면 (등교)",
    "service_date": "2026-10-19",
    "service_date_confirmed": true,
    "scheduled_stop_at": "2026-10-19T08:05:00+09:00",
```

### 기존 경로 조회와의 연결

기존 `POST /get_route_info`의 목적지 있는 응답은 `mode: "journeys"`, 출발·도착 정보, `journeys`, 기존 시내버스 필드·`source`를 유지한다. `shuttle`에 셔틀 서비스 응답 중 `journeys`를 제외한 조회 상태·출처·진단 메타데이터를 추가한다. 실제 후보는 공통 `journeys`에 통합한다. 목적지 없는 기존 주변 정류장 배열과 입력 오류 계약, 셔틀 서비스를 주입하지 않은 기존 `TransitService` 호출의 동작도 유지한다.

셔틀 후보는 기존 `legs`, 승하차 정류장, 접근·하차 후 도보 등 후보 구조를 따른다. 후보가 만들어지는 경우 교통수단과 출처는 후보별로 구분한다. 셔틀의 출처 때문에 기존 시내버스 `source`를 덮어쓰지 않는다. 시내버스 조기 반환이나 상위 후보 제한 때문에 셔틀 통합이 실행되지 않는 일이 없도록 한다. 통합 뒤의 개수 제한·정렬에서는 미확인 시간을 0으로 취급하거나 정보가 부족한 후보를 확정 최단 경로로 표시하지 않는다.

셔틀 서비스가 연결된 운영 경로 조회에서는 각 공급자의 조회를 분리하고, 아래 구조로 상태를 제공한다. 한쪽 공급자에 문제가 있어도 다른 쪽 후보가 있으면 HTTP 200 부분 응답으로 정상 후보와 `providers`·`warnings`를 반환하며 최상위 `error`를 넣지 않는다. 시내버스 조회가 실패하고 대체 셔틀 후보도 없으면 기존 HTTP 502와 `error`·`code`를 유지하면서 셔틀의 상태·진단도 함께 반환한다. 단순한 경로 없음과 조회 실패를 혼동하지 않는다. 현재 프론트는 최상위 `error`가 있으면 모든 경로 카드를 숨긴다.

```json
{
  "providers": {
    "city_bus": {"status": "...", "code": null},
    "shuttle": {"status": "...", "code": null}
  },
  "search": {
    "selection_policy": "transport_diversity_then_confirmed_total",
    "max_journeys": 3,
    "shuttle_max_transfers": 0
  }
}
```

최종 후보는 최대 3개다. 두 교통수단의 후보가 모두 있으면 각 수단의 첫 후보를 최소 1개씩 남긴다. 수단 사이의 시간 비교는 양쪽 모두 확인 가능한 `total_min`이 있을 때만 하고, 미확인 총시간 대신 `known_min`을 비교하지 않는다. 이는 후보 표시 정책이며 도시 전체 최단 경로나 셔틀의 실제 운행을 확정하는 정책이 아니다.

| 필드 | 의미·규칙 |
| --- | --- |
| `transport_type` | 셔틀은 `"shuttle"`, 시내버스는 `"city_bus"` |
| `time_basis` | 셔틀은 `"schedule"`. 시내버스는 `has_live_departure`가 참일 때 `"realtime_estimate"`, 그 밖에는 `"estimate"` |
| `realtime` | 셔틀 CSV에는 `false`. 시내버스에는 `has_live_departure`의 참·거짓을 적용. `arrival_reference_only`인 도착 참고값을 확정 실시간 출발로 승격하지 않음 |
| `scheduled_stop_at` | 정류장의 확인 가능한 시간표 시각을 조회 기준 날짜와 결합한 값. 날짜별 운행·시각 의미의 확인 상태와 함께 읽음 |
| `scheduled_departure_at` | 프로필에서 공식 확인한 제1노선의 원래 출발 이벤트만 채움. 제2~4노선은 의미 미확인으로 `null` |
| `scheduled_arrival_at` | 현재 운영 프로필에서는 도착시각을 확인하지 못했으므로 `null` |
| `service_date` | 조회에 적용한 시간표상의 날짜. 실제 운행 검증 여부는 아래 필드와 함께 읽음 |
| `service_date_confirmed` | 공식 프로필의 2026년 학기·요일·공휴일·예외 규칙 적용 범위에서 운행일 조건을 확인했는지 여부. 2027년 등 근거 범위 밖은 `false` |
| `scheduled_segment_min` | 양 끝의 원본 시각이 있을 때만 그 차이. 제1노선의 보완 종점처럼 시각이 없으면 `null`. 확정 `ride_min` 또는 `total_min`을 뜻하지 않음 |
| `ready_at` | 조회 시각에 대표점까지의 접근 도보와 앱 탑승 여유를 더한 조건부 준비시각 |
| `boarding_margin_min` | 적용한 앱의 승차 여유 설정값. 기본 1분 |
| `wait_min` | 승차 준비가 끝난 뒤 시간표 정류장 시각까지의 차이. 시간표 기반 값임을 함께 표시 |
| `arrival_min` | 셔틀 CSV에는 실시간 도착 정보가 없으므로 `null` |
| `has_live_departure` | 셔틀 CSV에는 `false` |
| `availability_confirmed` | 대표좌표·미확인 도착시간·실운행 조건이 남아 현재 셔틀 후보에는 항상 `false` |
| `known_min`, `known_min_complete` | 확인된 도보·여유·시간표 대기와 확인된 경우의 승차시간만 합산. 차량 시간이 빠지면 완전한 합계가 아니며 수단 간 최단 비교에 사용하지 않음 |
| `ride_min`, `total_min` | 현재 운영 프로필의 셔틀 후보에서는 `null`. 시간표 시각 차이를 넣어 확정하지 않음 |
| `location_is_approximate`, `path_basis` | 후보의 대표좌표 사용 여부와 지도 연결선의 `"reference_points"` 기준 |
| `warnings` | 미확인 운행 조건·시각 의미·좌표·데이터 오류 등을 사용자에게 설명 |

## 경완이에게 전달할 화면 연결 항목

게시 기준 `main`의 화면은 배열 응답만 지원한다. 목적지가 있으면 `data.find(...)`, 주변 목록에는 `data.forEach(...)`를 사용하므로 `journeys` 객체를 그대로 넘기면 정상 렌더링할 수 없다. 서버의 기존 목적지 API도 이미 객체를 반환하던 상태이므로 셔틀 필드만 몇 개 추가하는 것으로 해결되지 않는다. 백엔드 PR에서는 이 UI를 덮어쓰지 않는다.

고경완은 최신 HTML·CSS·화면 디자인을 유지하면서 다음 분기와 필드 어댑터를 별도 PR로 추가한다. 원래 작업폴더의 이전 UI 파일 전체를 복사해서 최신 디자인을 교체하지 않는다.

| 응답 | 화면 처리 |
| --- | --- |
| 최상위 `error` | 오류 메시지 표시 |
| `Array.isArray(data)` | 목적지 없는 기존 주변 정류장 배열 화면 유지 |
| `data.mode === "journeys"` | `data.journeys`를 후보 카드로 전달하는 새 분기. 시내버스·셔틀 공통 구조 사용 |
| `data.mode === "shuttle_timetable"` | 별도 시간표 화면을 만들 때 사용하는 계약. 일반 경로 카드로 자동 취급하지 않음 |

화면 표시 어댑터는 아래 내용을 지켜야 한다.

1. `journeys`의 `legs`, `access_walk`, `egress_walk`, `transfer_count`를 사용한다. 기존 배열 전용 `has_recommended_bus`·`matched_routes` 필드를 셔틀 후보에서 찾지 않는다. `static/js/api-service.js`와 지도 전달부에도 배열 전용 가정이 남았는지 확인한다.
2. 교통수단을 `transport_type`으로 구분하고, 셔틀에는 시간표 기반·실시간 아님을 표시한다. `arrival_min`이나 `has_live_departure`를 시간표 값으로 채워 실시간처럼 표현하지 않는다.
3. `scheduled_stop_at`, `service_date`, 운행일 확인 여부를 함께 표시한다. 제1노선은 공식 확인된 `scheduled_departure_at`을 시간표 출발로 표시하고, 제2~4노선은 정류장 시간표 시각으로 표시한다. 브라우저의 시간대와 무관하게 `Asia/Seoul` 기준으로 날짜·시각을 표시한다.
4. `scheduled_departure_at: null`·상대 종점 `time: null`을 0분이나 현재 출발·도착으로 해석하지 않는다. 시간표 정류장 시각·확인된 출발·미확인 도착을 구분한다. `ride_min`·`total_min`이 `null`이면 도착시각이나 총시간을 프론트에서 임의 계산하지 않는다. `Number(null)`이 0이 되는 변환도 피한다.
5. 시간표 대기 `wait_min`과 실시간 도착을 분리한다. `arrival_min: null`이어도 시간표 대기는 있을 수 있다. `known_min`은 미확인 차량 시간이 빠진 부분 합계이므로 “총 소요시간”이나 “최단 경로”로 표시하지 않는다.
6. 셔틀 노선명에 자동으로 `번`을 붙이지 않고 이름·방향을 표시한다. 시간표와 거리 추정 등 후보별 근거를 구분한다.
7. `location_basis`·`reference_name`·`official_stop_name`·`is_approximate`·`stop_location_verified`로 “정확한 승강장이 아닌 대표점”임을 안내한다. 교외의 `official_stop_name`은 원문 명칭일 수 있다. 제1노선 공식 CLC 안내를 제2~4노선의 승강장 확인으로 확대하지 않는다. 대표점까지 도보 0분을 실제 승강장까지 0분으로 표시하지 않는다.
8. API가 선택한 최대 3개 후보와 그 순서를 유지한다. 지도는 `legs[].board`·`alight`·`path`를 읽는 객체 분기가 필요하다. `path: []`이면 노선을 만들어 그리지 않고 `path_basis: "reference_points"` 연결선을 실제 도로·셔틀 궤적으로 표시하지 않는다.
9. 한쪽 공급자가 실패해도 다른 후보가 있으면 `providers`·`warnings`를 함께 안내한다. `shuttle.status`의 `not_operating`·`no_departures_remaining`·`unmatched`·미확인 운행일을 구분한다. **2026-10-18은 일요일이므로 프로필상 셔틀 후보가 없는 것이 정상**이며 다음 날 편을 오늘의 다음 차로 표시하지 않는다.
10. 2027년 등 운행일 근거 범위 밖, 프로필 해시 불일치와 `profile_status`, 데이터 오류를 표시한다. 수동 바인딩에 없는 정류장을 비슷한 정류장으로 대신 연결하지 않는다.

UI PR에서는 최신 디자인 유지, 목적지 유무에 따른 배열·객체 분기, 시내버스와 셔틀이 함께 있는 응답, `null` 시간, 일요일 빈 후보, 공급자 일부 실패, 지도 실패 중 카드 표시를 검증한다. 게시 기준 `main`의 `tests/frontend_smoke.cjs`는 **0바이트 빈 파일**이어서 Node 실행이 성공해도 아무 항목도 검증하지 않는다. 별도 UI PR에서 실제 내용이 있는 화면 테스트와 브라우저 확인을 마련해야 한다.

### 백엔드 병합 후 UI 작업을 받는 순서

이 절차는 백엔드 PR이 `main`에 병합된 **뒤** 고경완이 자신의 작업 사본에서 수행하는 안내다. 지금의 게시용 작업폴더나 다른 사람의 미커밋 파일에 실행하는 명령이 아니다. 먼저 `git branch --show-current`·`git status --short`·`git diff`로 본인 작업인지 확인하고, 수정 중인 본인 UI 파일만 골라 커밋해 보존한다. 아래 파일 경로는 예시이므로 실제 수정한 본인 파일만 선택한다.

```bash
git branch --show-current
git status --short
git diff
git add static/js/ui-renderer.js static/js/map-controller.js
git diff --cached
git commit -m "wip(ui): 진행 중 화면 작업 보존"
```

남은 변경이 있거나 작성자를 모르는 파일이 있으면 다음 단계로 넘어가지 않는다. 작업트리가 깨끗해진 뒤 자기 이름 브랜치의 원격 변경과 `main`의 백엔드를 받는다. 로컬 `main`을 기준으로 삼지 않는다.

```bash
git fetch origin
git switch 고경완
git pull --ff-only origin 고경완
git merge origin/main
```

로컬 `고경완` 브랜치가 **없는 경우에만** 두 번째 줄 대신 `git switch --track -c 고경완 origin/고경완`을 사용한다. switch가 실패했다고 무조건 이 명령을 실행하지 않는다. `pull --ff-only`가 분기 때문에 거절되거나 merge 충돌이 있으면 현재 이력을 보존하고 담당자와 해결한다. 강제 push·`reset --hard`·일괄 덮어쓰기를 사용하지 않는다.

최신 백엔드를 받은 뒤 위 필드 어댑터를 연결하고 검증한다. 완성한 본인 UI 파일만 선택해 커밋한 다음 `git push origin 고경완`으로 올리고, GitHub에서 **base `main` / compare `고경완`**인 별도 UI PR을 만든다. PR 본문에는 배열·`journeys` 객체 분기, 셔틀 시간표·대표좌표·미확인 시간 표시와 검증 내용을 적는다. API 필드 변경이 필요하면 이준엽과 먼저 협의하며, `git pull origin 고경완`만으로 `main`의 백엔드가 자동 반영된다고 생각하면 안 된다.

## 검증

외부 API를 호출하지 않는 `unittest`를 우선 사용한다. 원본 로딩·회차·행 보존과 운영 프로필 적용은 실제 CSV·프로필·프로젝트의 건물 및 시내버스 좌표 자료로 검증한다. 접근 도보·출발 경계·조건 분기·자정 넘김·오류 격리는 고정 시각과 모의 도보 함수·합성 fixture로 검증한다. 합성 좌표·운행 조건은 운영 데이터에 저장하거나 학교 공식 자료로 취급하지 않는다.

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest discover -s tests -p 'test_shuttle*.py'
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest discover -s tests
git diff --check
```

검증 시 실제 원본 읽기, 같은 방향·회차의 순서, 제1노선 공식 구간 보완과 도착시각 `null`, 접근 도보 동안 놓치는 편, 준비 완료 직전·정각·직후, 막차 후·자정, 금요일 예외·학기·휴일·2027년 미확인, 대표점 필드 보존, 보류 명칭, 원본 해시 불일치, 잘못된 행의 격리, 시내버스·셔틀의 양방향 실패 격리와 기존 API 계약을 확인한다. 시내버스 좌표를 읽지 못해도 시간표는 조회할 수 있는지 확인한다. 실제 자료에 없는 시간·조건은 합성 자료의 검증 범위를 따로 보고한다.

이전 단계에서는 실제 CSV 시간표에 테스트 전용 좌표 매핑과 도보 2분을 주입한 Flask 검증으로 `ready_at` 07:53·시간표 대기 5분과 시내버스 실패 중 셔틀 반환을 확인했다. 이때의 좌표는 합성 자료였고 운영 매핑에는 저장하지 않았다. 당시 프로필 없는 기본 설정의 GPS 결과는 `unmatched`였다.

현재 운영 설정은 공식 프로필과 사용자가 승인한 실제 자료의 대표점 바인딩을 주입한다. 연결 가능한 구간에는 후보를 반환하며, 검증되지 않은 정류장 연결은 계속 제외한다. 실제 프로필·대표점으로 조회한 고정 시각의 API 사례와 테스트 결과는 이번 단계의 최종 검증 후 별도 기록한다.

공식 자료 읽기와 API 실호출 검증은 구분한다. 실제 TMAP/TAGO API·브라우저·현장 승차 위치 검증은 이 오프라인 절차에 포함되지 않으며, 화면 후속 작업까지 완료됐다는 뜻도 아니다. 정확한 셔틀 승강장, 미확인 명칭의 대응, 도착시간·차량 이동시간, 근거 기간 밖의 운행 조건은 추가 자료가 필요하다. 원본과 관련 없는 기존 작업을 보존하고 의존성을 임의 설치하지 않는다.

이전 구현 단계는 Git 추가·커밋·push·브랜치 변경·PR 작업을 하지 않는 보호 조건으로 진행했다. 이후 사용자가 별도로 승인한 **게시 단계**는 최신 `main`에서 분리한 작업폴더의 백엔드·데이터·테스트·이 문서 등 허용된 14개 파일만 대상으로 한다. 원래 작업폴더의 미커밋 변경과 최신 UI를 옮기거나 덮어쓰지 않고 게시 담당자가 별도 검증·PR 절차를 수행한다. 이전 단계의 Git 제한을 승인된 게시 작업의 실행 결과와 혼동하지 않는다.
