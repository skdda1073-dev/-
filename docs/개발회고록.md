문제 인식: 하지만 막상 화면을 보니 직관적이지 않았습니다. 10분 뒤에 버스가 오고 3분을 걸어야 한다면, 당장 학생 입장에서 "그래서 지금 당장 뛰어나가야 하는가?"를 판단하기 어려웠습니다.

Phase 3. 하드웨어의 벽 (맥북 GPS 실시간 연동 에러)
에러 발생: '내 실시간 위치' 기능을 테스트하는데, 어느 순간부터 브라우저에서 "GPS 신호가 약합니다"라며 위치를 아예 잡지 못하는 치명적인 버그가 터졌습니다.
원인 분석: 스마트폰과 달리 맥북(노트북)에는 GPS 안테나 칩이 없어 주변 Wi-Fi 신호를 긁어모아 위치를 삼각측량합니다. 그런데 코드에 고정밀 GPS 옵션(enableHighAccuracy: true)과 캐시 미사용(maximumAge: 0)이 걸려 있어, 브라우저가 짧은 시간 내 무리한 Wi-Fi 스캔을 반복하다 타임아웃(에러)을 뱉어낸 것입니다.
해결 (하이브리드 스캔): 맥북의 하드웨어 특성을 고려해 위치 데이터의 수명(캐시)을 1분으로 연장하고, 고정밀 스캔이 막힐 경우 즉각 일반 스캔 모드(enableHighAccuracy: false)로 재시도하게 만드는 예외 처리 코드를 작성해 안정성을 극대화했습니다.
Phase 4. 외계어의 습격과 네이버 지도를 향한 진화 (목적지 검색 로직)
기능 고도화: 출발지만 보여주는 것을 넘어 "남춘천역" 등 '목적지'를 입력하면 타야 할 버스를 추천해 주는 기능을 추가했습니다.
에러 발생: 화면에 300번, 15-S번 같은 예쁜 노선 번호 대신 CCB250030000 같은 시스템 코드가 섞여 나오고, 길 건너편 하행선 정류장까지 '추천 정류장'으로 동시에 뜨는 버그가 발생했습니다.
원인 및 해결: 공공데이터포털의 API 반환값 중 춘천시 고유의 CCB 시스템 ID가 사용자 노선 번호 란에 섞여 들어오는 현상이었습니다. 이를 막기 위해 백엔드(app.py)에서 딕셔너리를 이원화하여 시스템 ID와 순수 노선 번호의 매칭 로직을 완전히 분리하고, 목적지행 버스가 있는 단 하나의 최적 정류장만 걸러내도록 로직을 수정했습니다.
Phase 5. 정보의 홍수를 통제하다 (화이트 테마 & 타임라인 UI 개편)
문제 인식: 기능이 많아지다 보니, 목적지를 검색했을 때 화면 위아래로 온갖 정류장과 수많은 버스 목록이 주르륵 나열되어 오히려 가독성이 떨어졌습니다.

원인 및 해결: 로컬 환경에서 깃허브로 파일을 올릴 때, 최상단에 파일을 올리지 않고 hallym_capstone 폴더 자체를 드래그 앤 드롭하다 보니 hallym_capstone/hallym_capstone/app.py 구조의 마트료시카 현상이 발생한 것입니다. Render 클라우드는 가장 바깥쪽 과거 파일을 읽고 있었습니다. 이를 깨닫고 클라우드 CI/CD 설정(Settings)에서 Root Directory를 직접 지정해 줌으로써 마침내 최신 버전 배포에 성공했습니다.

## UI/UX 1차 개선 — 지도 중심의 통학 경로 안내 화면

### 1. 작업 개요

한림대학교와 강원대학교 학생을 대상으로 하는 통학 정보 서비스에서, 목적지를 검색하고 출발 위치를 설정한 뒤 이동 경로를 확인하는 화면을 개선하였다.

이번 작업은 UI/UX 담당 범위의 1차 개선이다. 기존 백엔드가 제공하는 장소 검색·주변 정류장·경로 후보 정보를 활용하여, 사용자가 정보를 입력하고 결과를 확인하는 프런트엔드 구조를 재구성하였다.

- 대상 브랜치: `고경완`
- 작업 범위: HTML, CSS, JavaScript 및 브라우저 테스트
- 변경 규모: HTML 1개, CSS 4개, JavaScript 7개, 테스트 1개로 총 13개 파일

### 2. 문제 정의와 개선 목표

통학 중에는 출발 위치와 목적지를 설정하고, 이용할 정류장과 이동 경로를 빠르게 파악할 수 있는 화면이 필요하다. 이에 따라 이번 작업에서는 다음 세 가지를 설계 목표로 설정하였다.

1. 목적지 검색, 출발지 설정, 경로 조회를 하나의 흐름으로 연결한다.
2. 지도와 경로의 핵심 정보를 함께 확인할 수 있도록 배치한다.
3. 위치 권한 거절, 검색 실패, 시간 정보 미확인 상황에서도 사용자가 다음 행동을 선택할 수 있도록 안내한다.

현재 목표는 통학 상황을 기준으로 설정한 UI 설계 가정이며, 실제 학생 대상 사용성 평가를 통해 추가로 검증할 예정이다.

### 3. 디자인 선택과 구현 내용

Citymapper 앱의 큰 지도, 초록색 패널, 흰색 검색 카드 구성을 시각적 참고 자료로 활용하였다. 이를 프로젝트의 학교 선택·교내 건물 출발·주변 정류장 조회 기능에 맞게 재구성하였다.

| --- | --- |
| 지도 중심 레이아웃 | 모바일에서는 지도 아래에 검색 패널을 배치하고, PC에서는 지도 왼쪽에 패널을 배치하여 화면 크기에 맞게 정보를 제공한다. |

### 4. 구현 과정에서 확인한 문제와 해결

**지도 로딩 지연과 검색 화면 초기화**

구조 검토 과정에서 외부 지도 SDK를 앱 스크립트보다 먼저 불러오면, 지도 응답 지연이 검색 화면 초기화까지 늦출 수 있는 문제를 확인하였다.

이를 해결하기 위해 검색 UI를 먼저 초기화한 뒤 지도 SDK를 비동기로 불러오도록 변경하였다. 지도 응답이 늦거나 실패하는 상황에서도 검색과 결과 표시를 사용할 수 있도록 구성하고, 해당 상황을 브라우저 테스트에 포함하였다.

**검색 결과의 갱신 순서**

사용자가 검색어를 빠르게 바꾸면 이전 요청의 응답이 늦게 도착하여 최신 결과를 덮어쓸 수 있다. 요청 취소와 최신 요청 확인 처리를 적용하여 현재 입력에 해당하는 결과를 유지하도록 정리하였다.

**로컬 프로젝트 적용**

수정본을 적용하는 과정에서는 패치 파일이 명령어를 실행한 프로젝트 폴더에 없어 파일을 찾지 못하는 오류가 발생하였다. 패치 파일을 프로젝트 최상위 폴더에 배치한 후 `git apply --check`로 적용 가능 여부를 확인하고 실제 적용을 진행하였다.

### 5. 검증 결과

AI 작업 환경에서 Playwright를 이용한 브라우저 점검 10개 그룹이 통과하였다.

주요 확인 항목은 다음과 같다.

- 360px·390px 모바일 및 1440px PC 화면에서의 배치와 가로 넘침

- 빈 결과·통신 오류 이후 재검색
- 위치 권한 거절 후 교내 건물 선택으로 진행
- 지도 SDK 실패·지연 중 검색 기능 유지
- 이전 검색 응답이 최신 결과를 덮어쓰지 않는 처리

이 검증에서는 지도·장소·버스·위치 정보에 모의 응답을 사용하였다. 따라서 실제 API 인증, 실제 기기의 위치 정확도, 버스 도착 정보의 정확성까지 확인한 결과는 아니다.

이후 Windows 로컬 프로젝트에 패치를 적용하고 화면 디자인을 확인하였다. 사용자 만족도나 검색 시간 단축에 대한 정량적 평가는 아직 진행하지 않았다.

### 6. 담당 역할과 생성형 AI 활용

UI/UX 담당 범위에서 참고 디자인과 개선 방향을 정하고, 학교·교내 건물·현재 위치를 활용하는 통학 서비스의 화면 요구사항을 제시하였다. 생성된 수정본을 로컬 프로젝트에 적용하고 디자인을 확인하였다.
