# 전국 통학과 춘천 시내 경로 계산

## 전국 통학 길찾기

`학교에서 출발`과 `학교로 가기`에서 한림대·강원대 춘천캠퍼스의 건물, 전국 주소·장소, GPS, 지도 좌표를 지정할 수 있다. 출발 시각은 한국 시간으로 입력한다. 결과 카드는 선택한 건물부터 첫 승차 지점까지의 도보, 정차·승차 지점, 환승 이동과 대기, 마지막 도보, 전체 도착 시각을 보여준다. 자정을 지나면 날짜가 바뀐 시각을 표시한다.

`POST /api/journeys`는 좌표가 확인된 장소 또는 학교 건물과 `departure_at`을 받는다. `GET /search_poi?scope=national&q=...`는 전국 장소 검색을 사용한다. 춘천 시내와 주변 정류장 화면은 기존 `/get_route_info` 계약을 사용한다.

철도·도시철도는 국가철도공단·코레일 운행표와 [가공 데이터](../data/TRANSIT_DATA.md)를 읽는다. 실측 도보 시간은 TMAP 보행자 경로를 조회한다. 정차 순서만 확인되는 지역 버스는 경로를 표시하되 소요시간은 비워 둔다. 시외버스는 확인 가능한 승차시설과 버스타고 당일 배차를 연결한다. 예매 링크는 코레일, 버스타고 등 해당 구간에서 확인된 예매처를 열며, 운임·배차 변경·잔여석은 예매처에서 확인한다.

2026-09-01 시행분부터 8호선은 서울교통공사의 전체 운행표를 사용한다. 별내·다산을 포함한 같은 열차의 정차 시각을 연결하고, 별내역에서 경춘선과 8호선 사이의 환승 보행과 대기를 계산한다. 이 두 구간도 다른 후보와 함께 도착 시각으로 비교한다.

철도·전철은 춘천역과 남춘천역에서 시내버스 및 운행일과 정차 시각이 확인된 셔틀 후보를 비교한다. 철도를 타러 갈 때는 정류장에서 내린 뒤 역까지 걸어간 시각에 탈 수 있는 열차를 찾는다. 춘천에서 내릴 때는 도착 열차별로 역에서 정류장까지 걷는 시간까지 적용해 다음 버스를 확인한다. 즉시 출발에서 확인된 TAGO 승차 예측을 쓰며, 미래 연결은 확인된 정류장별 공개 시각표가 있어야 총시간에 포함한다.

춘천 밖의 목적지는 주변 버스 정류장부터 노선의 진행 방향을 거슬러 올라가 최대 8km 이내의 철도역에서 갈아탈 수 있는 버스를 찾는다. 최대 8개 환승역의 철도 도착 시각을 한 번의 시간표 탐색에서 계산한다. 역에서 정류장까지의 TMAP 도보와 1분의 승차 여유보다 먼저 떠나는 버스는 제외한다. 마지막 도보까지 합친 목적지 도착 시각을 기존 전철·철도 경로와 비교한다. TAGO가 정류장 순서와 방향 및 이용 가능한 버스 도착을 제공하는 지역에서 동작한다. [TAGO 버스도착정보](https://www.data.go.kr/data/15098530/openapi.do)

금곡역에서 덕소 방면으로는 땡큐61·땡큐88-1·땡큐99가 `GGB222000381`(금곡역.어룡마을입구.주유소) 44번 정차점에서 `GGB222001004`(동부센트레빌.덕소아이파크) 69번 정차점까지 운행한다. 경기버스정보의 정차 순서와 요일별 첫차·막차·배차 범위를 연동했다. ETA를 확인할 수 없는 경우 평균 배차 간격의 절반을 예상 대기로 사용하고, 버스 탑승 시간은 정류장 거리 기준으로 추정해 카드에 표시한다. 시간표 검색에서 버스의 실제 주행 시간과 미래 실시간 도착을 확인하려면 추가 자료가 필요하다. [경기버스정보 마을버스 노선현황](https://www.gbis.go.kr/service/busInfo/townBus.action?centerId=4136000000&cmd=townBus) · [정류장 순서 CSV](../data/normalized/bus/gyeonggi_bus_transfer_sequences_20261125.csv) · [배차 CSV](../data/normalized/bus/gyeonggi_bus_transfer_frequencies_20261125.csv)

한림대학교 의학관에서 덕소아이파크아파트(37.58753949, 127.22274818)까지 2026-11-26 한국 시간으로 조회했다. 16:00 출발에서 기존 전철 환승 도착은 18:36으로 표시됐다. 금곡역 버스 환승 예상 도착은 하차 정류장과 보행 조회 결과에 따라 18:31~18:32로 표시됐다. 07:30 출발에서는 기존 전철 환승(09:58)이 금곡역 버스 환승 예상(10:18)보다 빨랐다.

ITX-청춘은 춘천·남춘천과 청량리·용산 사이의 양방향 운행편을 출발 날짜별로 조회해 철도 탐색에 넣는다. 계획 승하차 시각과 구간 운임은 TAGO 응답을 사용하며, 자정을 넘는 도착 날짜를 유지한다. 이 조회는 기존 열차 시간표 화면과 같은 `TRAIN_API_KEY`를 사용한다. [TAGO 열차정보 API](https://www.data.go.kr/data/15098552/openapi.do)

춘천을 오가는 버스타고 당일 편은 두 터미널에서 각각 도보, 이용 가능한 버스, 철도·전철 연결을 비교한다. 시외버스 출발 5분 전까지 터미널에 도착할 수 있어야 하며, 하차 후 연결은 시외버스의 도착 시각부터 계산한다. 시외버스의 예상 도착에는 도로 상황에 따른 변동이 있다.

시내버스 300번은 2026-11-20~30의 춘천역→한림대학교, 한림대학교→남춘천역, 춘천시외버스터미널→한림대학교를 추가로 연결한다. 춘천시 노선책자의 기점 시각 42회와 춘천시대중교통정보의 예정 시간 차를 TAGO 정류장 ID·방향·순번에 대조했다. 예약 경로에서는 공개 시각표 기반 추정으로 표시한다. [시내버스 검증 데이터](../data/normalized/bus/chuncheon_ride_time_estimates.json)

경로 추천은 요청 출발부터 최종 목적지까지 도보·대기·탑승·환승을 포함한 도착 시각을 비교한다. 도착 시각이 같으면 환승이 적고 그다음 도보가 짧은 경로를 우선한다. 출발·도착 시각이 일부 빠진 후보는 `partial`로 표시한다. 인천 2호선의 일부 전철 시각, GTX-A, 일부 지역 버스와 도서 구간은 제공 범위나 API 활용 권한에 따라 연결이 제한될 수 있다.

## 현재 운영 방식

시내버스 경로는 TAGO의 정류소·노선상세·경유정류소 API를 연결해 계산한다. `app.py`는 `TransitService`에 로컬 CSV 노선망을 주입하지 않는다. 표시할 버스번호는 같은 노선 ID의 공식 노선상세에서 확인하며, 조회 실패를 오래된 CSV나 ID 끝자리로 대체하지 않는다.

`data/raw/bus/chuncheon_bus_routes_20260326.csv`와 CSV 저장소·검증 코드는 셔틀 정류장 참조 및 기존 데이터 검증을 위해 보존한다. 이 파일의 300·400번 기록이 현재 시내버스 추천의 근거는 아니다. 원본 출처·손상된 번호·기준일 혼합은 `../data/README.md`를 참고한다.

결과는 제한된 범위에서 찾은 직통·1회 환승 후보다. API의 정류장 순서만으로 실제 배차, 종점 회차 후 연속 탑승, 도시 전체 최단 경로 또는 네이버 지도와 같은 결과를 보장하지 않는다.

## 필요한 API와 설정

| 기능 | 설정·활용신청 | 미설정·실패 시 |
| --- | --- | --- |
| 주변 정류소와 정류소별 경유노선 | `TAGO_API_KEY` 우선, 없으면 `PUBLIC_DATA_KEY`, [TAGO 버스정류소정보](https://www.data.go.kr/data/15098534/openapi.do) | 시내버스 노선망을 조회할 수 없음 |
| 공식 노선번호와 전체 경유 순서 | 같은 키, [TAGO 버스노선정보](https://www.data.go.kr/data/15098529/openapi.do) | 확인하지 못한 노선은 제외. 권한 오류는 `ROUTE_PERMISSION` |
| 실시간 버스 도착 | 같은 키, [TAGO 버스도착정보](https://www.data.go.kr/data/15098530/openapi.do) | 도착·대기 정보 미확인. 노선망 조회 성공 여부와 별도로 안내 |
| 연결된 경기 마을버스 실시간 도착 | `GBIS_API_KEY`, [경기도 버스도착정보 API](https://www.data.go.kr/data/15080346/openapi.do) | 요일별 공개 배차로 추정. 2026-11-25 기존 공공데이터 키로는 금곡역 항목의 권한 오류(HTTP 403)를 확인 |
| 외부 장소 검색과 실제 도보 시간·거리 | `TMAP_APP_KEY` | 교내 건물 검색은 가능하나 일반적인 접근·하차 후 도보를 확인할 수 없음 |
| 네이버 지도 SDK | `NAVER_MAP_CLIENT_ID` | 지도 표시 불가. 서버 경로 응답과 별개 |

정류소정보·노선정보·도착정보는 별도 API 서비스다. 같은 인증키로 정류소·도착 조회가 성공해도 노선정보 서비스의 활용신청·인증 반영까지 확인된 것은 아니다. 네이버 지도 SDK는 지도 표시에 사용하며, 이번 구현에 네이버 대중교통 길찾기 API를 새로 연결하지 않았다. TMAP 대중교통 길찾기 상품도 사용하지 않는다.

기존 다른 계정의 `PUBLIC_DATA_KEY`를 보존하면서 버스 전용 `TAGO_API_KEY`를 따로 설정할 수 있다. 세 시내버스 API는 선택된 버스 키 하나를 함께 사용한다. 기존 `TAGO_API_KEY`를 쓰던 ITX 조회·수집은 `TRAIN_API_KEY`에 이전 키를 보존하고 이를 우선 사용한다. 시외버스 등 기존 공용 키 소비처는 그대로 유지한다. `/health`의 `configured.tago_api_key`는 대체 키까지 고려한 버스 키 존재 여부이며, `checks.bus_routes.key_setting`은 선택한 변수명만 표시한다. 키 값은 응답하지 않는다.

실행 환경·키 입력·실호출 점검은 `BACKEND_SETUP.md`를 따른다. 프로젝트 루트 `.env`를 읽으며 터미널·배포 환경의 명시적 설정이 우선한다. 실제 키는 저장소·채팅·캡처에 올리지 않는다. 키를 바꾸면 서버를 다시 시작한다.

## 조회와 계산 순서

1. 좌표기반 근접정류소 `getCrdntPrxmtSttnList`에서 출발지·목적지 반경 500m 정류소를 조회하고, 각각 가까운 최대 8개를 선택한다. 춘천 도시코드는 `32010`이다.
2. `getSttnThrghRouteList`의 정확한 `routeid`로 후보 노선을 모은다. 정류장명이나 버스번호가 같다는 이유로 다른 ID를 합치지 않는다.
3. 각 후보 ID에 대해 `getRouteInfoIem`을 단건 조회한다. 정확히 같은 `routeid`와 비어 있지 않은 `routeno`를 확인해야 한다. 정류소 경유정보의 번호와 다르면 공식 상세번호를 쓰고 경고를 남긴다. 노선 ID 숫자로 번호를 추정하지 않는다.
4. `getRouteAcctoThrghSttnList`에서 해당 노선의 정류소 전체 페이지를 수집한다. `routeid`, `nodeid`, `nodeord`, 좌표, 선택 항목인 `updowncd`를 사용한다. 누락·반복 페이지와 ID 불일치는 오류로 처리한다. 공식 노선번호나 순서를 확인하지 못한 노선을 CSV로 되돌려 추천하지 않는다.
5. 유효한 `updowncd`가 있으면 `api_direction`으로 같은 방향의 연속 순번만 연결한다. 상·하행마다 순번이 1부터 다시 시작하는 응답도 방향별로 나누며, 같은 방향의 중복 순번은 거절한다.
6. 상·하행이 누락되거나 유효하지 않은 응답은 `api_order` 후보로만 처리한다. 순번이 증가하는 연속 구간만 허용하고, 확인된 방향 경계를 넘지 않는다. 역순 이동·마지막→처음 자동 연결·임의 회차 연결은 하지 않는다. 반복 정류장 방문은 각각 보존한다.
7. 직통 공통 노선을 우선하며 API 조회는 최대 32개 노선으로 제한한다. 같은 정류장 ID에서 서로 다른 노선 ID·버스번호 사이의 1회 환승만 허용한다. 맞은편 승강장이나 이름만 같은 정류장은 합치지 않는다.
8. 접근·하차 후 도보는 TMAP의 실제 보행 응답으로 확인한다. 실패를 직선거리 시간이나 가짜 0분으로 대체하지 않는다. 한쪽의 모든 도보가 실패하면 `WALK_UNAVAILABLE`로 안내한다. 정확히 같은 좌표의 도보만 0분이 가능하다.
9. 도보 조회 뒤 새 실시간 도착정보를 받는다. 노선 ID·방향·승차 방문을 구분할 수 있는 경우에만 도보 도착 후 승차 여유를 비교한다. `api_order`의 도착값은 참고용이며 총시간 계산에 사용하지 않는다.
10. 탑승 시각을 평가할 수 있는 직통 후보에는 실제 접근·하차 도보를 적용한다. 참고 후보는 최대 80개를 평가한다. 끝까지 시간이 계산된 시내버스·셔틀 후보를 총시간, 환승 수, 도보시간 순으로 비교해 최대 3개를 표시한다. 두 번째 버스의 미래 배차는 확인된 시간 자료가 있어야 합산할 수 있다.

API 호출 구현은 `services/public_transit_client.py`, 조회 연결은 `services/transit_service.py`, 외부 호출 없는 탐색은 `services/route_planner.py`가 담당한다. 노선상세·경유노선·경유정류소 조회는 1시간 캐시를 사용하고, 실시간 도착은 캐시하지 않는다. 따라서 운행 개편 직후의 즉시 반영까지 보장하지 않는다.

## 방향·시간·지도 표시

### 지도에서 두 지점 선택

지도 상단의 **출발지 선택**을 누르고 위치를 클릭하면 도착지 선택으로 이어진다. 두 지점이 정해지는 즉시 기존 `/get_route_info`에 좌표로 요청하고, 기존 장소 검색과 같은 결과 패널에 로딩·경로 목록·상세를 표시한다. 데스크톱은 오른쪽, 작은 화면은 기존 결과 영역을 사용하며 지도 위에 별도 결과 카드를 만들지 않는다. 선택 후 일반 지도 클릭은 위치를 바꾸지 않으며, 출발지·목적지 버튼으로 다시 선택하면 자동 재조회한다. 초기화·메뉴 변경·기존 검색 입력 변경은 진행 중 요청과 이전 추천을 무효화한다. 지도 좌표는 GPS 위치 캐시나 기존 검색 입력에 덮어쓰지 않는다.

`static/js/map-journey-controller.js`는 좌표 선택·위젯 드래그만 맡고, `api-service.js`의 공통 `requestRoute`와 `ui-renderer.js`가 모든 경로 조회·결과 표시를 처리한다. `app-shell-controller.js`가 같은 결과 패널의 열기·닫기·검색 수정 상태를 관리하고, `map-controller.js`가 선택 핀과 정류장 연결선을 담당한다. 지도 조회의 ‘검색 수정’은 기존 GPS·건물 입력을 덮어쓰지 않고 지도 출발지 재선택으로 돌아간다. `templates/index.html`에는 위젯 마크업만, `static/css/map-journey.css`에는 해당 오버레이 스타일만 둔다.

지도 선택과 일반 검색은 서버가 반환한 같은 후보 목록·인덱스와 카드 형식을 사용한다. 각 카드에서 공식 번호·방향·승차 직후 정류장과 대기 확인 수준을 표시하며, 불완전한 후보는 참고 경로로 안내한다. 대표점 기반 셔틀 후보를 운행·탑승 가능 확정으로 표시하지 않는다.

모든 경로 조회에서 출발지→목적지 전체의 TMAP 보행 시간·거리를 먼저 확인하고 `direct_walk: {status, minutes, distance_m, source}`로 반환한다. 그 뒤 버스·도착을 조회해 보행 API 대기 때문에 실시간 도착이 낡는 일을 줄인다. 실제 보행 조회 실패는 `unavailable`과 null로 두고, 직선거리나 임의 속도로 대체하지 않는다. 같은 좌표일 때만 0분·0m이며, 다른 좌표의 0·음수·비유한수·잘못된 응답은 사용할 수 없다. 공급자 오류로 HTTP 502가 되어도 함께 성공한 `direct_walk`는 위젯에서 사용할 수 있다.

공통 경로 카드는 기존 승차 안내·버스번호·방향·시간 표시 아래에 전체 도보 시간을 짧게 표시한다. 버스 전체에는 정류장까지의 도보, 도착 후 정류장 대기, 탑승, 환승 여유, 하차 후 도보가 포함된다. `total_min`, 전체·구간별 `wait_min`, 도보·탑승 시간과 사용할 수 있는 실시간 출발을 함께 확인해야 도보와 비교한다. 대기나 실시간 정보가 없으면 도보 시간은 표시하되 더 빠르다는 문구는 표시하지 않는다. `known_min`을 총시간으로 대체하지 않는다. 전체 도보가 더 짧으면 차이를 표시하며 도보를 추천하고, 가까운 스쿠터도 확인할 수 있다고 안내한다. 스쿠터의 재고·접근 시간·주행 경로·소요 시간은 확인하지 않았으므로 스쿠터가 빠르다고 단정하지 않는다. 버스 도착까지 남은 시간은 정류장 도착 후의 대기와 구분한다. 지도 점선은 비교용 버스 정류장 연결선이다. 긴 경고는 기본적으로 접힌 ‘경로 정보 안내’에 둔다.

버스 후보가 없거나 조회에 실패해도 전체 도보를 확인했다면 같은 결과 패널에 도보 대안 카드를 표시한다. 오류 원인은 접힌 안내에 보존한다. 지도 선택도 일반 검색과 동일하게 택시 API를 자동 호출하지 않으며, 택시는 기존 택시 메뉴에서 별도로 조회한다. 교통수단별 요금의 종합 비교는 제공하지 않는다.

### 근거리 이동 추천

`services/travel_recommendation.py`는 외부 호출 없는 추천 계산만 담당한다. `TransitService.plan`이 확인된 `direct_walk`와 반환 후보 목록을 전달하고 `recommendation`을 응답에 추가한다. `ui-renderer.js`는 도보가 우선인 경우 같은 오른쪽 결과 영역 맨 위에 추천을 보여주며, 기존 버스 카드는 ‘버스 대안’으로 보존한다. 후보의 원래 인덱스·지도·상세 선택은 바꾸지 않는다.

- 대기 미확인 안내에는 전체 도보 15분·1km와 필수 보행 비교 여유 2분을 사용한다.
- 버스 총시간에는 정류장까지 도보·대기·탑승·환승 여유·하차 후 도보가 모두 있어야 한다. 비교할 수 있는 총시간과 도보 시간이 있으면 짧은 쪽을 추천하고, 동점이면 환승 수와 도보 시간을 비교한다.
- 도보가 확인된 버스보다 충분히 짧으면 그 차이를 표시한다. 예를 들어 도보 7분·버스 19분이면 도보가 약 12분 짧다는 근거를 먼저 표시한다. 검색 결과 범위의 비교이며 전체 교통망의 최단시간을 보장하지 않는다.
- 대기가 미확인이라도 전체 도보가 모든 비교 가능한 버스 후보의 필수 보행시간보다 2분 이상 짧으면 정류장 우회가 불리하다는 근거로 추천할 수 있다. `ride_min` 추정값을 확정적인 하한으로 쓰지 않는다. 후보별 최소값은 실제 후보를 가리키며 서로 다른 후보의 부분 시간들을 합쳐 가상 경로를 만들지 않는다.
- 시간 비교가 불완전해도 짧은 구간은 편의성 차원에서 도보를 안내할 수 있다. 이때 ‘가장 빠르다’거나 대기 포함 절약시간을 표시하지 않는다.
- 킥보드는 보행 참고거리 300m~2km·도보 25분 이내에서 조건부 대안으로 안내한다. 실제 기기 재고·기기까지 접근·대여 준비·허용 경로 주행·반납 후 도보가 확인되지 않았으므로 `scooter.total_min`은 null, 가용성·경로 확인은 false로 둔다. 보행 경로 거리를 킥보드 주행거리로 바꾸거나 임의 속도로 확정 도착시간을 만들지 않는다.

공유 PM API는 별도로 승인돼도 지역 지원을 확인해야 한다. [공공데이터포털 공식 명세](https://www.data.go.kr/data/15117668/openapi.do)의 `PersonalMobilityInfo/GetPMProvider`·`GetPMListByProvider`는 운영사·탑승 가능 기기 목록이며 주행 경로·소요시간 API가 아니다. 2026-11-21 읽기 검증에서 `cityName=춘천시` 요청은 성공했지만 반환된 2개 운영사의 실제 지역은 모두 세종특별시였다. 따라서 요청 필터나 승인 여부만으로 춘천 기기 가용성을 단정하지 않는다. [TAGO 연계 현황](https://tago.go.kr/v5/link/current_data.jsp)의 공유 PM 표도 세종을 안내한다. 운영 코드에는 이 검증용 호출이나 키를 추가하지 않았으며, 춘천 기기·허용 주행 경로 데이터가 연결될 때까지 조건부 추천만 제공한다.

점선은 `legs[].path`의 정류장 좌표를 순서대로 연결한 참고선이다. 도보 구간이나 택시의 실제 도로 경로선을 만들지 않는다. 현재 지도 선택·버스 방향·추천 카드에는 추가 공공데이터 신청이 필요하지 않다. 정확한 도로 선형, 셔틀 승강장·운휴·이용조건, 비용 비교까지 확장하려면 각 정보의 확인된 데이터가 추가로 필요하다. 네이버 길찾기 API는 추가하지 않는다.

각 버스 구간에 `next_stop`을 내려준다. 이 값은 **승차한 방문 바로 다음 정류장**의 ID·이름·좌표이며, 하차 정류장 다음이나 노선 첫 정류장을 뜻하지 않는다. 화면은 이를 “다음 정류장 ○○ 방면”으로 표시한다. `api_order`일 때 이 안내는 API 순서 기준이고 실제 상·하행·회차 검증을 대신하지 않는다.

- 버스 이동시간은 연속 정류장 직선거리 합 × 1.2, 평균 시속 20km, 중간 정류장당 0.4분 정차로 추정한다. 시간표·실제 도로·교통량 기반 값은 아니다.
- `known_min`은 확인된 도보, 추정 버스 구간, 환승 여유와 사용할 수 있는 대기를 합한 값이다. 대기나 방향이 미확인이면 전체 도착시간으로 해석하지 않는다.
- `api_order`는 `direction_verified: false`, `arrival_reference_only: true`, `total_min: null`, `wait_min: null`을 유지한다. 도착 참고값이 있어도 탑승 가능이나 전체 도착시각을 확정하지 않는다.
- 방향 정보가 있어도 탈 수 있는 도착값이 없거나 반복 방문을 구분할 수 없으면 대기·총시간을 미확인으로 둔다. 환승 경로의 미래 배차도 미확인이다.
- 지도는 첫 후보의 승하차 정류장과 연결선을 표시한다. 연결선은 실제 버스 주행·도보 궤적이 아니다.

## 응답과 오류

목적지가 없으면 기존 주변 정류장 배열을 유지한다. 이 화면도 API 운영 모드에서는 도착정보의 `routeid`를 공식 노선상세로 확인하며, 공식번호와 충돌하는 도착 항목은 제외한다. 공식 상세를 확인하지 못하면 임시 번호를 표시하지 않고 빈 `buses`와 `arrival_error`로 안내한다. 목적지가 있으면 다음과 같은 경로 응답을 반환한다. 아래는 방향 정보가 없는 경우의 구조 예시이며 실제 운행 결과가 아니다.

```json
{
  "mode": "journeys",
  "origin": {"name": "출발", "lat": 37.88, "lon": 127.73},
  "destination": {"name": "도착", "lat": 37.86, "lon": 127.72},
  "journeys": [],
  "source": {
    "source": "api",
    "sequence_basis": "api_order",
    "number_basis": "tago_route_info"
  },
  "warnings": [],
  "search": {
    "max_transfers": 1,
    "nearby_radius_m": 500,
    "max_stops_per_endpoint": 8,
    "max_routes": 32,
    "max_reference_candidates": 80
  }
}
```

각 후보에는 `legs`, `access_walk`, `egress_walk`, `transfer_count`, `known_min`, `total_min`, `total_unavailable_reason`, `warnings`가 있다. 각 구간의 `sequence_basis`와 `direction_verified`로 방향 확인 수준을 판단한다. `legs[].next_stop`은 `{id, name, lat, lon}`이며 `board`, `alight`와 같은 정류장 형식이다. 방향 미확인의 총시간 누락 이유는 `direction_unverified`, 배차 미확인은 `wait_unknown`이다.

주요 오류는 `PUBLIC_DATA_KEY_MISSING`(노선망 키 미설정), `ROUTE_PERMISSION`(노선 API 권한), `ROUTE_DATA`(노선 ID·공식번호 불일치/미확인), `WALK_UNAVAILABLE`(보행 조회), `NETWORK`·`INCOMPLETE`(연결·목록 완전성)다. 시내버스 실패와 셔틀 조회 상태는 `providers`로 구분하며, 가능한 셔틀 후보가 있으면 별도로 남는다. 빈 경로 목록은 제한된 검색 범위에서 후보를 못 찾았다는 뜻이지 실제 버스가 없다는 판정은 아니다.

`GET /health`는 외부 호출 없이 로컬 준비만 확인한다. `routing_mode`는 `tago_route_candidates`, `checks.bus_routes.source`는 `tago`다. 키가 있으면 `checks.bus_routes.status`는 `configured`지만, 외부 인증 성공을 뜻하지 않으며 `external_apis_verified`는 항상 false다. 현재 준비 판정에는 캠퍼스·셔틀 참조 CSV·TMAP 키·공공데이터 키가 필요하다.

## 확인된 사실과 남은 검증

2026-11-21 실호출 조사에서 같은 설정의 공공데이터 키로 정류소정보와 도착정보가 정상 응답했다. 정류소별 경유노선 목록에는 한림대 두 승강장 `CCB250001275`, `CCB250002127`에서 300번이 있었고 400번은 없었다. 포스코더샵A `CCB250001295`에는 300·400번이 모두 있었다. 따라서 목적지 쪽에서 400이 보인다는 사실만으로 한림대에서 400을 타는 연결을 만들면 안 된다.

초기 조사에서는 기존 설정 키로 노선상세·경유정류소 조회가 HTTP 403, `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`(반환 코드 30)로 거절됐다. 이후 포털의 실제 승인 상태와 키를 대조해 **승인된 계정의 키와 프로젝트 설정 키가 서로 다름**을 확인했다. 사용자 승인 후 `TAGO_API_KEY`만 승인된 키로 연결했고, 노선상세·경유정류소·정류소·도착 조회가 모두 정상 응답했다. 기존 공용 키는 유지하고 이전 열차 키를 `TRAIN_API_KEY`로 보존했으며 열차 도시코드 API도 정상 응답했다. 코드 30은 미등록, 31은 만료로 구분하고 HTTP 403 안의 안전한 제공기관 오류코드도 보존한다.

자동 검증은 모의 API로 공식번호 우선, ID 끝자리 추정 금지, 승차 직후 `next_stop`, 방향 없는 API 후보, 역순·회차 자동 연결 금지, 방향 경계와 방향별 순번 재시작, 페이지 완전성·권한 오류를 확인한다. `tests/test_live_transit_routing.py`는 이 중 새 번호·방향 계약의 회귀를 담당한다. 기존 CSV 검증은 보존된 자료의 처리 규칙을 확인하는 것으로, 현재 운영 노선의 정확성을 입증하지 않는다. 프런트엔드 모의 검증도 실제 지도 SDK·브라우저 운행 검증을 대신하지 않는다.

2026-11-21 [네이버 지도 대중교통 화면](https://map.naver.com/p/directions/3zNyU2,2AZvjF,%ED%95%9C%EB%A6%BC%EB%8C%80%ED%95%99%EA%B5%90,11591671,PLACE_POI/3zO1Z1,2AZeNi,%EB%A7%A5%EB%8F%84%EB%82%A0%EB%93%9C%20%EC%B6%98%EC%B2%9C%ED%9B%84%ED%8F%89DT%EC%A0%90,38491102,PLACE_POI/-/transit)를 직접 확인했다. 출발지는 개별 건물 대신 한림대학교 대표장소다. 직통 최적 경로는 300번이며 한림대학교→성심경로당→봉의중학교→크로바A→포스코후문→포스코더샵A 순서였다. 이 사례의 안내 기준은 “300번 · 다음 정류장 성심경로당 방면”이다. 400번은 다른 환승 대안의 두 번째 구간에 표시되므로 목적지에 전혀 갈 수 없는 노선이라고 단정하지 않는다. 네이버 API 호출이나 시간표 복사는 하지 않았다.

기존 5050 개발 서버가 여전히 CSV 모드였던 것도 확인해 프로젝트 경로·PID를 대조한 뒤 최신 코드로 재시작했다. `/health`의 `tago_route_candidates`와 `TAGO_API_KEY` 선택을 확인했다. 재시작한 실제 사이트에서 의학관→맥도날드 춘천후평DT점 검색·길찾기는 HTTP 200으로, 첫 후보가 **300번 · 다음 정류장 성심경로당 방면 · 포스코더샵A 하차**였다. 공식 300번 경유 57개와 상·하행 코드도 확인했다. 당시 탑승 가능한 실시간 대기는 미확인이라 총시간은 비워 두었다.

확인한 사례를 모든 건물·모든 시각의 추천 검증으로 확대하지 않는다. 최초 검색은 캐시가 없는 노선의 상세·순서를 여러 번 조회하므로 응답시간과 호출량도 계속 확인해야 한다.

검증 명령은 `BACKEND_SETUP.md`의 회귀 테스트와 실호출 점검을 참고한다. 커밋·push·병합·운영 배포는 이 문서 갱신에 포함하지 않는다.

## 춘천 300번 공개 시각 연동과 재현 조건
